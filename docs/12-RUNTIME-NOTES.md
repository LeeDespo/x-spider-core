# 12 · 下载运行时与 sidecar 注记

本文档是下载运行时与 sidecar 的深层注记：两个下载引擎（内置 HTTP / Aria2Next 外派）的行为语义、
断点与下载记录、队列状态机（暂停 / 恢复 / 取消 / epoch）、以及 sidecar 的生命周期
（父进程看门狗、幂等命中与恢复入口）。每条都来自一次真实返工，格式为「现象 → 根因 → 解法（含证据）」。

分工边界：配置与分发事实（sidecar 形态、aria2-next 的版本与分发、打包、交叉编译）在 `docs/03`；
测试纪律与 fixture 规则在 `docs/04`；引擎语义的 X 侧背景（404 报成功、JSON-RPC 错误码坍缩、
媒体真实大小只有 CDN 知道）在 `docs/02` §E；`dl.*` 的对外入参出参与错误码以 `docs/CONTRACT.md`
与 `docs/07` 为准。

条目编号沿用原 AGENTS.md 踩坑记录的编号（因此不连续，这里只收录下载运行时与 sidecar 相关的
14 条）；正文中引用的其它坑号（如踩坑 8）可在 `docs/05-WORKFLOW.md` 的踩坑总索引里查到对应条目。

## 踩坑记录（2026-10-06 迁入自 AGENTS.md，保留原编号）

**22. Aria2Next 对 404 会报"成功"，并留下 0 字节文件。**
- 现象：`aria2.addUri` 一个不存在的 URL，`tellStatus` 返回
  `status=complete, errorCode=0, completedLength=0, totalLength=0`，
  磁盘上多了一个 **0 字节文件**。
- 根因：这是 aria2-next 的行为（不是 bug，就是它的语义），
  而 `docs/02` §E2 早就警告过"不能只看引擎的结论"——这次是现场证据。
- 解法：完成判据是**我们自己的落盘字节数 + `expect_size` 校验**；
  `crates/xspider-download/tests/aria2_e2e.rs::a_404_must_not_be_reported_as_success` 钉住它。
- 相关：坑 23（同一引擎的错误语义）、坑 31（`expect_size` 从哪来）；
  同一实测的背景记录见 `docs/02` §E6。

**23. Aria2Next 的 JSON-RPC 错误全是 `code: 1`，且 `--help` 不完整。**
- 现象 A：`Unknown option` / `GID ... is not found` / `Unauthorized` 三种完全不同的原因，
  返回的都是 `{"error":{"code":1,...}}` → 按码分类在这层不可用，按文案分类是铁律禁止的。
- 现象 B：`--split` / `--max-connection-per-server` 在 `--help=#all`（180 个选项）里**找不到**，
  但 `aria2.getGlobalOption` 读得到（值 6）——**它们是可用的**。
- 解法：① 选项名在自己这边钉死（只用手测确认过的）；② GID 记账在本地，
  RPC 错误一律当"后端异常"，`message` 只作诊断；
  ③ **确认选项存不存在要问运行中的实例**（`getGlobalOption`），别信帮助。
- 相关：坑 22、坑 24（同引擎的语义）。背景见 `docs/02` §E7；
  另注：现象 B 的结论后来被复测收窄——这两个上游多连接选项在当前 Aria2Next 路径已退役，
  组件改用实测有效的 `stream-max-connections`，见 `docs/02` §E8。

**24. 两个下载引擎的断点不能共用，靠文件名在物理上隔开。**
- 现象（推演 + 设计规避）：内置 HTTP 后端追加的是原始字节，aria2 还额外维护
  `.aria2` 控制文件；把两者的半成品拼起来会产出**损坏文件**（`docs/02` §E3）。
- 解法：断点名带引擎标识（`.part.http` / `.part.aria2next`），
  于是"换个引擎接着用别人的断点"在物理上不可能发生——
  比"记得在代码里判断引擎有没有变"可靠。
- 相关：坑 22、坑 23（两个引擎各自的行为语义）；引擎断点、控制文件与临时文件的背景见
  `docs/02` §E3–§E5。

**26. 过期结果会覆盖新状态：每次派发都要有 epoch。**
- 现象：暂停之后立刻恢复，任务又变回 `error`（reason=cancelled）——暂停像是没生效。
- 根因：恢复会立刻派发新一轮，而上一轮的任务还在收尾；它返回时把"已取消"写进了状态。
- 解法：任务只在自己那一轮（`epoch` 匹配）里落状态与发事件，否则静默丢弃。
  同类问题在"重试 + 超时"里都会出现，用 compare-and-swap 的思路一次解决。
- 相关：坑 27（终态落在什么时刻）、坑 44（这一课的续集：epoch 防住了状态，
  还防不住文件 I/O 与派发轮次）。

**27. 取消不能提前把状态标成终态。**
- 现象：测试断言"取消后不留临时文件"偶发失败。
- 根因：`cancel()` 立刻把状态写成 `error`，而字节还在流、清理还没发生——
  外壳去看的那一刻，状态与事实是矛盾的。
- 解法：在飞的任务由**真正停下来的那一刻**落终态；排队中的任务才立刻终态。
- 相关：坑 26、坑 44（同属"状态与事实一致"的时序问题）。

**28. 下载记录里必须存 url，只存"下到哪了"是没法续传的。**
- 现象：重启恢复的任务在记录里找得到，却无法重新排队。
- 根因：记录里只有 `dest_path` 与 `bytes`，没有源地址。
- 解法：`RecordEntry` 增加 `url` / `expect_size`（外加 `version` 字段）。
  **记录格式是契约级别的资产**：它决定"重启后能不能对账"，漏字段要等重启才暴露。
- 相关：坑 40（重启对账之后，"恢复"该走哪个入口）。

**29. "先探测再绑定"的端口分配有竞态，启动要能换端口重试。**
- 现象：Aria2Next 的 E2E 在并行跑时偶发失败（引擎没起来）。
- 根因：`free_port()` 是"绑 0 拿端口 → 释放 → 交给子进程"，两个测试可能拿到同一个端口。
- 解法：`spawn` 失败时**换端口重试 3 次**（产品/参数类错误不重试）。
  这不只是测试问题——真实使用里也会撞上。
- 相关：坑 36（子进程 / sidecar 生命周期的另一侧）。

**31. 实测出来的一个真缺口：媒体下载原本"无法校验完整性"。**
- 现象：`Media` DTO 里没有大小字段，于是 `dl.enqueue` 拿不到 `expect_size`，
  所有媒体下载都落在 `Integrity::Unverified` 分支。
- 影响：`docs/02` §E2 说"完整性校验是唯一的成功判据"，而未校验意味着
  截断的文件也会被当成功。
- 解法：**队列自己在下载前探测**（`probe_size_when_unknown`，默认开）。
  顺带解决了另一件事：引擎选择（内置 / Aria2Next）本来就要看大小，现在它拿得到真值。
- 相关：坑 22（`expect_size` 是完成判据的另一半）。探测的两条路
  （先 `HEAD`、失败退回 1 字节的 `Range`）与"码率 × 时长会差 5 倍"的实测背景见 `docs/02` §E9。

**32. 组件漏了参考实现早就传的头：下载请求的 UA 与 Referer。**
- 现象：审计时对照 `x-spider-mac/.../Aria2Engine.swift`，发现它给 aria2 显式传了
  `user-agent`（Chrome 142 macOS）与 `referer=https://x.com/`，而本组件的
  内置后端与 aria2 后端**都没传**——reqwest 的默认 UA 是 `reqwest/0.12`。
- 根因：抽取时只搬了"下载逻辑"，没搬"请求长什么样"。
- 解法：两个后端都带上同一个 UA + Referer，并加 `Accept-Encoding: identity`
  （否则服务端压缩时 `Content-Length` 是压缩后大小，与实际落盘字节数对不上，
  完整性校验会**假红**）。
- 教训：**凡是"请求长什么样"这类事实，参考实现已经有答案，先去看它。**
- 相关：坑 33、坑 34（同一轮审计里抓出来的代理类问题）。

**33. 外派后端的代理必须逐任务显式传——子进程不认识 `HTTPS_PROXY`。**
- 现象：审计发现 `aria2.addUri` 的选项里**从来没有代理**，而 `x-spider-mac`
  是逐任务传 `all-proxy` 的。
- 影响：在"需要代理才能出网"的机器上，内置后端正常、外派后端全挂——
  两个后端行为不一致，而契约承诺它们行为一致。
- 解法：`DownloadRequest.proxy_url`（由 `ProxyConfig::resolve_url()` 解析成**具体 URL**，
  `Env` 分支读 `HTTPS_PROXY`/`ALL_PROXY`），aria2 侧写成 `all-proxy`。
- 教训：**"进程内能自动读到的东西"到了子进程就要显式给**，别假设它会继承。
- 相关：坑 32、坑 34。

**34. "运行中可改"的配置，只要有一条路径没跟上，就比不支持更坏。**
- 现象：`net.set_proxy` 改了代理后取数立刻恢复，但下载队列在创建时**快照**了代理，
  于是下载仍在走旧出口（或已不可达的旧端口）。表现为"列表刷得出来、文件一个都下不动"。
- 根因：队列的配置在 `start` 之后不可变，而代理**是会变的**（踩坑 8：一天变三次）。
- 解法：`HttpDownloader` 的客户端放进 `RwLock` 并加 `set_proxy`；
  `DownloadQueue::set_proxy` 两个后端一起换；`Engine::set_proxy` 在队列已起来时转发。
  代理在**派发那一刻**读，不是入队那一刻。
- 已知未覆盖：`net.set_limits` 的并发上限仍是启动时值（信号量不能缩容），需要时再补。
- 相关：坑 33（子进程侧要显式传代理，进程内则要可运行中更换）。

**36. 外壳被强杀时，组件会变成孤儿——必须自带父进程看门狗。**
- 现象：`xcodebuild test` 收走测试宿主（SIGKILL）之后，`~/Library/.../XSpiderCore/xspiderd`
  仍然活着；再跑一次测试就又多一个，累积成一堆没人管的组件在后台跑。
- 根因：优雅退出靠外壳调 `system.shutdown`，而**强杀不会调**——改代码、调试器停进程、
  测试宿主被收走，全都是强杀。组件的 `--stop-with-process` 管的是**它自己的子进程**（aria2），
  救不了它自己。
- 解法：`xspiderd` 启动时记下 `parent_id()`，每 2 秒比对一次：变了（被 reparent 到 launchd）
  就自己优雅退出。实测日志：`父进程已消失，组件自行退出（避免留下孤儿） original=3298 now=1`。
  实现在 `bins/xspiderd/src/main.rs` 的 `spawn_parent_watchdog`。
- 教训：**"父进程死了就跟着死"要在子进程自己身上实现**，不能指望父进程一定会收尾。
- 相关：坑 29（启动期的端口竞态，同属子进程 / sidecar 生命周期）。

**40. `already_known` 是"幂等命中"，不是"重新开始"——恢复任务要用 `dl.resume`。**
- 现象：接入后的外壳把"继续"实现成再 `dl.enqueue` 一次（同一个 `job_id`）。
  组件照约定回了 `already_known`，**任务原地不动**——界面显示"下载中"，
  而组件里的任务还是 `paused`，进度永远停在断点处。失败重试同理（任务在 `error` 上）。
- 根因：`job_id` 幂等是为了解决「跨页重复投递 / 暂停后重试 / 重启对账」，
  所以"同 id 第二次入队"必须是**无操作**；而"恢复"是另一个语义。
- 解法：`dl.resume` 对 `paused` / `error` 显式恢复；`waiting` / `active` 保持成功但不重复派发，
  `complete` 被拒绝。取消清理期间暂拒恢复。详见 `docs/07` §4.4 与 §7.3。
- 教训：**幂等键保护的是"不要重复做"，不提供"再来一次"**。把两者混在一个入口上，
  症状是"看起来在跑、其实没跑"——比直接报错难查得多。
- 相关：坑 28（重启对账依赖记录格式里存了什么）。

**44. epoch 防住旧状态，防不住旧请求写同一个断点；派发也必须校验调用方那一轮。**
- 现象：审查 1.5.2 的暂停/恢复路径时，发现旧下载尚在收尾，新轮次已可写同一 `.part`；
  更隐蔽的是旧 resume 捕获 token 后被新 pause/resume 超越，延迟 dispatch 会把新 runner 的
  epoch 作废，留下 Waiting 却没有有效 runner。
- 根因：epoch 原来只在结果落状态时校验，文件 I/O 没有所有权串行化，dispatch 也只检查当前状态。
- 解法：每个 job 的 backend/finish 持有异步 run gate；dispatch 接收 expected_epoch
  并在状态锁内校验。`queue_e2e::rapid_pause_then_resume_serializes_the_old_backend_run`、
  快速 pause→cancel→resume 与 `queue::tests::stale_dispatch_cannot_invalidate_a_newer_resume`
  钉住它。
- 同轮修复：取消清理失败后不能仅按 Active 状态假定 runner 仍存在；改按 run gate 判断，
  并允许重复 cancel 收尾。Active 的 control 路径变成目录的故障注入 E2E
  可抓住“失败后永久 Active”的旧行为。
- 文件归属：入队时目标不存在不等于取消时目标归本任务；Waiting/Paused/pending-cancel 恢复
  只删断点，保留不能证明归属的完整文件。不能为了“干净”误删另一个任务或用户的文件。
- 相关：坑 26（epoch 的第一课：只挡过期状态）、坑 27（终态落在真正停下来的那一刻）。
