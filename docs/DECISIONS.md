## ADR-001 首批支持平台：macOS 为唯一交付目标，其余保持"可编译"
- **背景**：初期的平台范围取舍；当前验收范围由 ADR-038 与 ADR-042、`docs/03` §6 维护。
- **选项**：A 三平台同做 / B 先 macOS，架构上不堵死其它 / C 只做 Linux 服务端
- **决定**：**B**。M0–M2 只对 macOS arm64 做端到端验收；代码不引入任何 Apple 专有依赖
  （不用 Keychain / Security.framework），HTTP 用 rustls，路径处理不假设 POSIX。
  Linux/Windows 的 CI 与交叉编译放在 M3。
- **理由**：真正存在的消费方只有 `x-spider-mac`；先把一条链路做对，比三条链路都做一半有价值。
- **代价**：Windows 的路径/大小写不敏感等问题要到 M3 才暴露。
- **何时该推翻**：出现第二个真实消费方时。

## ADR-002 sidecar 传输：本地 HTTP JSON-RPC 为主，stdio 为备选
- **背景**：需要在 sidecar 与进程内调用之间确定主次，形态说明见 `docs/01` §1 与 `docs/03` §3。
- **选项**：A 只 HTTP / B 只 stdio / C 两者都做且 HTTP 为主
- **决定**：**C**。`--port 0` + ready 行 + 随机 token；stdio 作为无端口环境的备选。
- **理由**：HTTP 与 aria2 一致、可直接 `curl` 调试、天然多请求；**实测依据**是 sidecar 形态
  不受 hardened runtime 影响（`docs/03` §1），而 dylib 形态会死。
- **代价**：要处理端口、token、单实例与残留进程（冒烟脚本已断言无残留）。
- **何时该推翻**：如果外壳全部转向进程内 cdylib，且愿意接受 `disable-library-validation`。

## ADR-003 下载引擎：aria2 外派为主、内置 HTTP 兜底，且内置后端在 M1 就要有
- **背景**：下载后端要覆盖多连接需求，同时提供零外部依赖的兜底，边界见 `docs/01` §5。
- **选项**：A 只用 aria2 / B 只用内置 HTTP / C aria2 为主 + 内置兜底
- **决定**：**C**，并接受"内置 HTTP 后端不是可有可无"：它是**零外部依赖的保底**，
  也是离线测试的唯一载体（本地 HTTP fixture server 能造 Range/断流/慢速/404）。
- **理由**：aria2 是 GPL-2.0 的独立程序，只能"聚合"不能吸纳代码；而"没有 aria2 二进制也能工作"
  是跨端可用性的最低要求。
- **代价**：两套后端的**行为一致性**要靠同一套 `requirements` 表达，且引擎切换必须丢弃断点
  （`docs/02` §E3）——这是实现期最容易出错的地方。
- **何时该推翻**：如果内置后端在真实网络下的吞吐不可接受，把它降级为"仅测试用"。

## ADR-004 组件 A / B 会在同一进程内被同时加载，但**不共享**限流状态
- **背景**：合并到同一个 sidecar 进程时，限流状态要不要合并？配额域依据见 `docs/02` §B6。
- **选项**：A 全局一个闸门 / B 按配额域分桶（API / CDN）/ C 按组件分桶
- **决定**：**B**。限流按**配额域**分，而不是按组件或全局分。
- **理由**：`docs/02` §B6 的实测结论是"接口受账号配额、CDN 是另一套"。
  两套配额混在一起，一边被限流会把另一边冻住——这正是把 fetch 与 download 拆开的理由之一；
  合并部署不能让这个理由失效。
- **代价**：如果将来出现第三个配额域（例如搜索端点独立配额），要加一个 `RequestClass` 变体。
- **何时该推翻**：如果实测发现两类请求共享同一配额窗口。

## ADR-005 `x-spider-mac` 接入：先走「外壳提供 aria2 路径」
- **背景**：接入阶段需要决定 Aria2Next 由组件随包携带还是由外壳提供路径；方案见 `docs/03` §4。
- **决定**：接入初期走 **B（外壳提供路径）**，复用现有分发；随包携带（A）留到 M3 打包时再定。
- **理由**：`x-spider-mac` 现在已经能自己分发 aria2-next，先接组件、别同时改分发方式，
  否则出问题时分不清是组件还是打包。
- **代价**：外壳多一个配置项。
- **何时该推翻**：第二位消费方出现时——那时"外壳提供路径"会变成每家都要配一遍的负担。

## ADR-006 爬取循环：按「候选清单 + 策略参数」切分（确认而非推翻）
- **背景**：需要明确爬取循环由组件还是外壳负责，契约边界见 `docs/01` §4。
- **决定**：**照 `docs/01-ARCHITECTURE.md` §4 执行**，不推翻。特别保留三条：
  `wanted_keys` 进契约（它改变终止条件，成本相关）、`excluded_keys` 不进（外壳过滤，零额外请求）、
  `done_reason` 必须显式。
- **理由**：终止判据族（到底 / 时间推进 / 空页 / 游标未推进 / 收齐 wanted）是踩过最多坑的地方，
  把它参数化并归组件，是"一次写对"的前提。
- **代价**：外壳要理解 `done_reason` 的语义。
- **何时该推翻**：如果出现"外壳必须自己决定何时停止"的产品需求（目前没有）。

## ADR-007 `net.set_proxy` 进契约（对 `docs/01` §3 的加法式扩展）
- **背景**：`docs/01` 的取数契约里只有 `auth.set_cookie` / `net.set_limits` / `net.status`，
  没有代理配置。但**实测环境里代理端口会变**（同一天内出现 17890 → 12450 → 17890），
  靠环境变量重启进程才能换代理是不可接受的。
- **决定**：新增 `net.set_proxy {url}`（`null` = 关闭）。加法式演进，不改已有字段。
- **理由**：代理是**运行时可变的连接参数**，不是构建期常量。写进契约，外壳才能在设置页里改。
- **代价**：契约多一个 method；切换代理要重建 HTTP 客户端并重取签名密钥（已实现）。
- **何时该推翻**：如果某平台的外壳必须走系统代理、不允许进程级指定。

## ADR-008 参数严格校验：必填字段缺一不可，不做"部分更新"
- **背景**：`net.set_limits` 四个字段，是否允许只传其中一个？
- **决定**：**必填全部**。缺字段 → `invalid_request` 并**点出字段名**。
- **理由**：契约要能被机器校验（schema 里 `required` 与实现一致），
  而"部分更新"会让"当前值是什么"变成隐式状态——外壳改一个字段前得先读当前值。
- **代价**：外壳要一次给全（它有默认值，不难）。
- **何时该推翻**：如果真出现"只想改冷却时间"的常见场景，再加一个 `net.set_limits.patch`，
  而不是让 `set_limits` 变成可选的。

## ADR-009 401/403 时自愈一次：重载签名密钥后重试
- **背景**：X 的 401 有两个来源——cookie 真失效，或 `x-client-transaction-id` 过期/算法失效。
  两者在响应里**无法用结构化字段区分**（都可能是 401 + 同一 code），而文案匹配被铁律禁止。
- **决定**：首次 401/403 且带凭据时 → `signer.invalidate()` + 重试**一次**；
  仍失败 → `unauthorized`。
- **理由**：代价有界（最多多一次请求），收益是"X 轮换签名算法时组件能自愈，而不是逼用户重新登录"。
  而且 cookie 真失效时，重载密钥会在探测页就快速失败并返回 `unauthorized`，不会白等。
- **代价**：凭据真失效时多一次探测页请求。
- **何时该推翻**：如果实测发现"凭据失效"远比"签名过期"频繁，改成先查凭据再重载。

## ADR-010 离线（fixture 回放）模式**跳过请求签名**
- **背景**：签名密钥只能从真实登录态页面取；离线环境没有会话，硬要取就会发真实网络请求，
  违背铁律 3「默认离线测试」。
- **决定**：回放模式下不打 `x-client-transaction-id`，并记 debug 日志。
- **理由**：离线测试关心的是解析、分页、错误分类——都不经过签名。
  签名的正确性由 **live recorder + canary** 覆盖（本次实测已通过：真实请求返回 200）。
- **代价**：离线测试不覆盖"带签名的请求头组装"这一步。
- **何时该推翻**：如果我们能把签名密钥**录制**成 fixture 并离线复现（`page_artifacts.json`
  已经具备条件），就把它改成"回放时从 fixture 装载签名"，覆盖度更高。

## ADR-011 工具链：`channel = "stable"` + 注释记录实测版本，而不是写死版本号
- **背景**：`docs/05` §4 要求"锁定工具链（rust-toolchain.toml + Cargo.lock 入库）"。
- **实测**：写死 `channel = "1.98.1"` 会让 rustup 在首次构建时去下整个工具链，
  在代理环境下把 toolchain 装成半成品，报
  `could not remove 'component' file: .../manifest-rustfmt-preview-...`，
  并且之后**每次** cargo 调用都会尝试同步 channel（本地维护手册记录的工具链安装事故）。
- **决定**：写 `channel = "stable"`，并在文件里注释实测版本 `rustc 1.98.1 (48a229cea 2026-09-01)`；
  可复现性由 `Cargo.lock` + 注释里的版本号共同保证。
- **代价**：`stable` 会随时间前进，严格意义上不是"锁死"。CI 已经运行，但它不能消除代理下 rustup 固定版本安装半成品的本地问题；当前仍维持 stable。
- **何时该推翻**：出现可复现的工具链漂移问题，且固定版本在本地与 CI 的安装链路已验证可靠时，再评估精确 pin；仅仅有 CI 不构成推翻理由。

## ADR-012 cdylib 产物名固定为 `libxspider.*`
- **背景**：`docs/03` §5 约定的交付物是 `libxspider.dylib` / `.so` / `.dll`，
  但 cargo 默认按 crate 名产出 `libxspider_ffi.*`。
- **决定**：`crates/xspider-ffi/Cargo.toml` 里设 `[lib] name = "xspider"`，
  依赖方用 `use xspider::...`。
- **理由**：打包时不必改名，产物名与文档一致；`libxspider_ffi` 这种名字也不该出现在交付物里。
- **代价**：crate 名（`xspider-ffi`）与 lib 名（`xspider`）不同，读代码时要知道这一层。
- **何时该推翻**：不建议推翻。

## ADR-013 签名脚本扫描：顺序 + 总预算（而非上游的 16 路并发）
- **背景**：上游 `XClientTransaction` 用 16 路并发扫 bundle chunk，首个命中即止。
- **决定**：顺序扫描，最多 40 个脚本，**整体 45 秒预算**。
- **理由**：这是 1 小时一次的操作，省下 spawn/JoinSet 的生命周期复杂度；
  更要紧的是**有可证明的上界**——并发版没有总预算时，最坏情况能把 sidecar 挂住十几分钟
  （`docs/05` §6「不要加载到永远」）。
- **代价**：首次握手慢一些（实测 4 秒内完成，可接受）。
- **何时该推翻**：如果实测发现冷启动经常撞到预算。

## ADR-014 429 **一次都不重试**：直接记冷却并返回 `rate_limited`
- **背景**：上游 + `x-spider-mac` 都会对 429 做 3 次退避重试。
- **决定**：**不重试**。收到 429 → 记冷却（听 `Retry-After`，没有就用 `cooldown_s`，
  连续 429 退避放大到 15 分钟封顶）→ 返回 `rate_limited`。
- **理由**：重试限流响应是纯粹的行为放大：它让限流窗口更长，且消耗本已耗尽的配额。
  「越限越试」正是 `docs/02` §B7 要避免的。挂起与恢复应该由**调用方**看着
  `retry_after_s` 决定，而不是组件硬撑。
- **代价**：调用方必须处理 `rate_limited`（契约里已写明外壳该展示倒计时）。
- **何时该推翻**：如果实测发现 X 的 429 有"偶发误报、立刻重试就成功"的特征。

## ADR-015 `system.shutdown` 是 sidecar 传输层 method，不属于契约载荷
- **背景**：`docs/03` §3 要求支持收到 shutdown 时收尾。但 cdylib 形态没有"关掉宿主进程"这回事。
- **决定**：`system.shutdown` 只在 sidecar 实现，**不进** `xspider_call` 的 method 表，
  也不进 schema 的 `method` 枚举；在 `CONTRACT.md` §3.2 单独列一节，并在契约守卫测试里白名单化。
- **理由**：它是**部署形态的能力**，不是组件的能力。混进契约会让 cdylib 形态承诺一个做不到的事。
- **代价**：契约读者要多读一节。
- **何时该推翻**：不建议推翻。

## ADR-016 错误分类**只依据状态码与结构化 code**，绝不解析响应体文案
- **背景**：实测两种真实响应把这个决定逼出来了：
  1. **未登录**的请求返回 **HTTP 403 且响应体为空**——想从 body 里读原因根本没得读；
  2. **不存在的 screen_name** 返回 **HTTP 200 + `{"data":{}}`**——用状态码判断"不存在"也会错。
- **决定**：分类规则固定为「状态码决定大类（401/403→unauthorized，429→rate_limited，
  5xx→upstream）+ 结构化字段决定细分（`errors[].code` 数字枚举、`data` 里有没有 `user`）」。
- **理由**：铁律禁止用文案做判断；而这两条实测正好说明"结构"是唯一可靠依据。
- **代价**：如果 X 把 `user` 这个键改名，`{"data":{}}` 会被误判成 `not_found` 而不是 `parse`。
  兜底是**正向路径的 canary**（对真实用户断言解析成功）——改名会让正向用例立刻红。
- **何时该推翻**：如果 X 开始在 403 响应体里给结构化错误码，可以据此细分。

## ADR-017 `serde_json` 启用 `preserve_order`
- **背景**：JSON 对象的键序在语义上无关紧要，但有两处影响本仓库：
  `variables` 的键序希望与上游 `JSON.stringify` 一致；fixture 入库时希望保持响应的原始键序。
- **决定**：workspace 级启用 `features = ["preserve_order"]`。
- **理由**：让"与上游逐字可比"这个性质在**我们能看到的地方**都成立，
  减少一个排查时的变量；同时 fixture 与真实响应可以直接 diff。代价只是一个 indexmap 依赖。
- **代价**：`Map` 变成 `IndexMap`（多一个纯 Rust 依赖，GPL 兼容，无 C 工具链）。
- **何时该推翻**：如果依赖审计要求极限瘦身，且实测证明键序无影响。

## ADR-043 缺失字段按 DTO 语义区分 null 与省略
- **背景**：可选输出字段有两种既有序列化语义，不能概括成"缺失值恒为 null"。
- **决定**：`user.media_count` 与 `user.register_time` 缺失时保留显式 `null`；候选 `size_hint` 等带 skip-if-none 的字段无值时省略。
- **理由**：保持既有 DTO 与 schema 形状，不把 `None` 与 `0` 混同，也不向候选输出无意义的 null。
- **代价**：消费方按字段各自 schema 处理；不能对所有可选字段共用一条 null 规则。
- **何时该推翻**：如需统一可选字段表现，必须先作契约版本评估并迁移全部消费者。

## ADR-044 fixture 回放按请求特征打分选择样本
- **背景**：一个端点可能有多条录制响应，错误样本也需能在用户名变化后复用。
- **决定**：按 cursor (+8)、screen_name (+4)、operation (+2)、凭据类别 (+2)、HTTP method (+1) 计分，选择得分最高的 fixture。
- **理由**：分页游标最能改变响应语义；用户名、操作和鉴权类别细化场景；method 是最后区分因素。
- **代价**：新增同端点样本时需检查 `match_hint` 冲突，避免同分依赖枚举顺序。
- **何时该推翻**：若出现歧义或路由到错误场景，改用显式优先级/键并补匹配测试。

## ADR-018 用户结构**双形态兼容**：`legacy.*` 与 `core.*` / `avatar.*` 都认
- **背景**：实测同一批端点里两种用户结构并存（`user_medias`/`user_tweets` 用老结构，
  `search_timeline`/`home_timeline`/`following`/`tweet_detail` 用新结构，且新结构可能没有 `legacy`）。
- **选项**：A 只认老结构、等 X 统一 / B 只认新结构 / C 两套都认
- **决定**：**C**。用"候选路径"读字段（老结构优先、新结构兜底），两处解析共用同一组路径常量。
- **理由**：只认一种的失败方式不是"少几个字段"，而是**整页解析成空**并报 `parse`——
  那会让人误以为"X 大改版"，实际只是半边响应没读。上游 TS/Swift 也是这么做的。
- **代价**：每个字段多一层查找；错误信息要能说清"两种结构里都没有"。
- **何时该推翻**：如果 X 完全下线老结构，就把老路径删掉（并保留一条 canary 观察期）。

## ADR-019 所有分页端点统一返回 `items[]`（偏离 `docs/01` §3 的草图字段名）
- **背景**：`docs/01` 的草图里 `fetch.following` 写的是 `{users[], cursor?}`，其余是 `{items[], cursor?}`。
- **决定**：**统一用 `items[]`**，并在 `CONTRACT.md` 里写明。
- **理由**：外壳只需要写**一个**翻页循环；把 following 的数组叫 `users` 只会让外壳多一个特例，
  而特例就是 bug 的温床。这条偏离是加法式的（字段名不同，语义没变）。
- **代价**：与原草图的字段名不一致——已在 `CONTRACT.md` §3.1 与本文档记录。
- **何时该推翻**：不建议推翻。

## ADR-020 **客户端筛选清空一页不判"到底"**：游标照常返回、`end` 保持 false
- **背景**：`require_media=true` 时整页都可能是纯文字推文（实测 `user_tweets` 首页就是）。
- **决定**：`end` 只由"服务端是否给了游标"决定；被筛空时游标照常透传。
- **理由**：`docs/02` §D5 明确——到底判据只看服务端原始条数。判错会让爬虫在
  **这一页刚被筛空**时提前停止，表现为"某个账号只爬到一半"，而且很难归因。
- **代价**：调用方要能接受"成功但 `items` 为空且 `end` 为 false"这种响应。
- **何时该推翻**：不建议推翻。

## ADR-021 收下 `TimelinePinEntry`（置顶推文），与上游行为不同
- **背景**：置顶推文在**独立指令**里；上游 TS 与 Swift 移植都只遍历 `TimelineAddEntries`。
- **决定**：**收下它**，并在 `all_entries()` 里保持指令顺序。
- **理由**：实测它可能是整页**唯一带媒体**的那条（`user_tweets` 首页就是），
  丢掉它不是"少一条"，而是"这一页白翻了"。这是真实数据缺失，不是风格差异。
- **代价**：与上游/Swift 的输出可能差一条（同一页多出置顶那条）——已在 `docs/02` §H3 记录。
- **何时该推翻**：如果外壳明确要求"与 Swift 版逐条一致"，再加开关。

## ADR-022 请求构造收敛到 `calls.rs` 的**唯一实现点**
- **背景**：同一批请求有三处需要发出：端点方法、fixture 录制、canary 存证。
- **决定**：全部走 `RawCall` → `PreparedCall`（`calls::prepare`），录制与 canary 用同一个 `prepare`。
- **理由**：各写一遍的后果是**录下来的东西不代表生产行为**——fixture 会变成"我以为的请求"，
  而那正是 `docs/04` §2.1 要避免的。副产品：`cursor` 省略纪律、`@` 归一化、
  键序与上游一致，都只需在一个地方保证。
- **代价**：多一层间接；`prepare` 成了必须读懂的一处代码。
- **何时该推翻**：不建议推翻。

## ADR-023 搜索 queryId 自愈**带凭据**抓页面（推翻上游注释）
- **背景**：上游 Swift 注释说抓搜索页用 `cdnHeaders`（只有 UA）。
- **实测**：不带 cookie 访问 `/search` 会 307 到 onboarding 页（17KB，**无任何 bundle 引用**），
  带 cookie 才是 307KB 的真实 SPA 外壳。照上游做自愈**永远失败**。
- **决定**：页面请求带凭据、bundle 请求不带；两者都跟随重定向、都过 CDN 闸门。
- **代价**：自愈会向 x.com 带一次 cookie（同一个宿主，GraphQL 本来也带它）。
- **何时该推翻**：如果未登录访问 `/search` 的行为又变回返回 SPA 外壳。

## ADR-024 脱敏脚本自带**四条事后断言**（安全关键脚本必须有自检）
- **背景**：实测踩到过"新规则提前 return → 100+ 个真实 `rest_id` 原样入库"，
  而脚本正常退出、文件正常写入，肉眼看不出来。
- **决定**：`script/redact_fixtures.py` 跑完必须通过：
  ①原始长数字串 ∩ 输出 = ∅；②不同原始 id 不得洗成同一假值；
  ③原始 screen_name / 正文不得出现；④`match.cursor` 取值合法。
- **理由**：脱敏的正确性无法靠 review 保证（输出有几百 KB），只能靠断言。
  第 ②、③ 条还顺带保住了 fixture 的**语义有效性**（唯一性、可路由）。
- **代价**：脱敏脚本本身变长；断言误报时要先查是不是真泄漏。
- **何时该推翻**：不建议推翻——加规则时必须同步加断言。

## ADR-025 外派引擎**只支持 Aria2Next**，并且在启动时校验 `product`
- **背景**：`docs/03` §4 指定的是 fork `AnInsomniacy/aria2-next`；实测两者的选项集与行为不同
  （`--split`/`--max-connection-per-server` 在 Aria2Next 的 `--help` 里看不到但在 RPC 里可用；
  fork 专有 `--stream-max-connections`）。
- **选项**：A 只支持 Aria2Next / B 同时支持上游 aria2 / C 支持任意 aria2 系二进制
- **决定**：**A**。启动前用 `--version` 预检、启动后用 `aria2.getVersion` 的 `product` 复核；
  指向上游 aria2 会被明确拒绝（两处都在 `aria2.rs`，都有测试）。
- **理由**：混着支持意味着"同一份配置在这里能跑、在那里少一个选项"，
  而失败会以"下载不完整"这种最难查的形式出现。明确拒绝比静默降级好。
- **代价**：用户必须拿到 Aria2Next 的二进制（本机已有）。
- **何时该推翻**：如果上游 aria2 与 fork 的选项集重新收敛。

## ADR-026 引擎的半成品由**文件名**隔开，而不是靠"记得判断引擎有没有变"
- **背景**：`docs/02` §E3 要求"引擎与上次不同 → 丢弃断点"，否则拼接会产出损坏文件。
- **决定**：断点文件名带引擎标识（`.part.http` / `.part.aria2next`）。
- **理由**：靠代码判断"上次是哪个引擎"需要额外状态（而且跨进程重启就丢了）；
  靠文件名则是**物理上不可能误用**。这与 `docs/02` §E4 的"临时文件不能当引擎内部细节"
  是同一个思路：把它显式化。
- **代价**：`docs/02` §E3 的规则被"实现成"文件名差异，而不是一段判断逻辑——
  读代码的人需要知道这个约定（已写在两处注释与本节）。
- **何时该推翻**：不建议推翻。

## ADR-027 完成判据**永远**是落盘字节数，而不是引擎/后端的结论
- **背景**：实测 Aria2Next 对 404 返回 `status=complete` + `errorCode=0`，并留下 0 字节文件；
  内置 HTTP 后端也遇到过"服务端声明的大小与实际不符"。
- **决定**：两个后端走**同一套**校验：`expect_size` 给了就必须逐字节对上；
  没给时结果显式标为 `Integrity::Unverified`（**不允许**伪装成 `Verified`）。
- **理由**：`docs/02` §E2 说的就是这件事（"完整性校验是唯一的成功判据"）。
  两个后端各写一套校验，迟早会分叉。
- **代价**：调用方要提供 `expect_size` 才能得到 `Verified`（媒体下载场景里服务端都会给）。
- **何时该推翻**：不建议推翻。

## ADR-028 「被取消」不新增任务状态，用 `error.code = cancelled` 表达
- **背景**：任务状态机有 waiting/active/paused/error/complete 五个（`docs/01` §5.1），
  但取消需要一个终态。
- **选项**：A 加一个 `cancelled` 状态 / B 归到 `error` 并用 `error.code` 区分
- **决定**：**B**。
- **理由**：状态每多一个，外壳就多一条分支；而"取消"与"失败"在外壳侧的处理
  （停止转圈、不再重试）几乎一样，真正的区别只需要一个码。码是结构化的，够用。
- **代价**：外壳要先看 `state` 再看 `error.code` 才能显示"已取消"。
- **何时该推翻**：如果外壳普遍反馈"取消"需要独立文案 + 独立统计（那时加状态是加法式变更，不破坏兼容）。

## ADR-029 事件用「带游标的增量轮询」，不是推送流
- **背景**：`docs/01` §5.1 把 `dl.events` 写成 "(stream)"。
- **选项**：A HTTP SSE / WebSocket 推送 / B 每种传输各写一套流 / C 带游标的增量轮询
- **决定**：**C**。`dl.events {since}` 返回 `{seq, events[]}`；Rust 队列内部有 `subscribe()`，但不是对外 C ABI 或 JSON-RPC 接口。
- **理由**：契约要**语言中立且三种形态行为一致**——C ABI 与 stdio 都没有"流"的概念，
  给它们各造一套流等于把一致性交给运气。轮询在任何传输上都成立，且天然支持断线续读
  （`since` 就是游标）。事件日志是环形缓冲（2000 条），不是审计日志。
- **代价**：实时性取决于外壳的轮询间隔；事件超过缓冲会被丢弃（已文档化）。
- **何时该推翻**：如果外壳需要亚秒级进度且轮询开销不可接受——那时可以在 HTTP 形态上加 SSE，
  但**契约载荷不变**（仍是同一批事件），只是多一种传输方式。

## ADR-030 每个下载任务有 `epoch`，只有"当前这一轮"能落状态
- **背景**：暂停→恢复会立刻派发新一轮，而上一轮的任务可能还在收尾；
  实测：上一轮的"已取消"把新一轮刚设好的状态覆盖成了 `error`（暂停直接失效）。
- **决定**：派发时 `epoch += 1`；任务只在自己那一轮里落状态与发事件，
  发现 `epoch` 对不上就**静默丢弃**结果。
- **理由**：这是"重试与过期结果"的通用解法（compare-and-swap 的思路）。
  比"在取消时小心地清理标志位"可靠得多——后者要枚举所有交错顺序。
- **代价**：多一个字段与一次比较；读代码的人要知道它防的是什么（已写在字段注释里）。
- **何时该推翻**：不建议推翻。

## ADR-031 打包脚本自己验签；其三平台 CI 方案已由 ADR-038 收窄
- **背景**：macOS arm64 上未签名的可执行文件会被内核 SIGKILL（137，静默死亡），
  而"编译通过"完全不能说明"能在别的机器上跑起来"。
- **决定**：`script/package.sh` 打包后**必须 `codesign --verify --strict`**，失败即中断。
  原先提议的 Windows/Linux CI 格子已被 ADR-038 推翻；现有 macOS CI 保持，Android 构建检查由 ADR-042 增补。
- **理由**：签名这类"失败方式静默"的环节，脚本必须自己断言；
  而"写了 CI 配置"与"CI 是绿的"是两件事，混为一谈就是自欺。
- **代价**：跨平台运行时行为仍缺真实消费方验收；Android 的构建检查也不等于设备运行验收。
- **何时该推翻**：签名自检继续适用；新增平台的 CI 范围按对应 ADR 和消费方实测更新。

## ADR-032 队列自己探测大小（`HEAD` → 1 字节 `Range`），而不是拿码率估算
- **背景**：`docs/02` §E2 要求"完整性校验是唯一的成功判据"，但 GraphQL 的 media 对象
  里没有字节数，于是媒体下载全都落在"未校验"分支——这是一条实测出来的真缺口。
- **选项**：A 拿 `码率 × 时长` 估算 / B 下载时不校验 / C 问服务端 / D 让外壳自己先探测
- **决定**：**C**，并且放在**队列内部**（`probe_size_when_unknown`，默认开）。
- **理由**：A 被实测否掉——同一条视频估算 76 MiB、真实 14.48 MiB，**差 5.25 倍**
  （码率是编码器上限）。B 会让截断文件被当成功。D 把"下载前要先探测"变成外壳的责任，
  每个外壳都会漏。放在队列里还有两个附带好处：**引擎选择本来就要看大小**，
  现在它拿得到真值；而且探测只发生在真的要下载的文件上（爬取阶段不探，
  避免一页 20 个媒体白多 20 次请求）。
- **代价**：每个大小未知的下载多一次请求（`HEAD` 或 1 字节 `Range`，约几十毫秒）。
  探测失败不阻断下载（按"未校验"继续）。
- **何时该推翻**：如果 X 开始在 GraphQL 的 media 里给 `size`，就优先用它、把探测降级为兜底。

## ADR-033 `net.probe_size` 进契约：把"下载前的体积判断"交给外壳
- **背景**：ADR-032 让**组件**在入队后自己探大小，但外壳拿不到"下载前的体积视图"——
  想在"决定下不下"之前按大小过滤（例如"超过 100 MB 才外派 Aria2Next"、
  "太大的先问用户"），它只能自己再实现一套 CDN 探测。
- **选项**：A 不进契约，靠 `dl.enqueue` 的内部探测 / B 进契约，作为一个只读的 net 方法
- **决定**：**B**。`net.probe_size {url} -> {size: integer|null}`。
- **理由**：这是**数据获取**，不是下载调度——放 `net.*` 与 `net.status` 同类。
  它把"要不要花这次 CDN 请求"的决定权还给外壳；组件内部的自动探测（ADR-032）
  仍然是缺省行为，两者不冲突。
- **代价**：契约多一个 method（只增不改不删，就此固化）。多次调用会重复消耗 CDN 配额——
  这是调用方的责任，契约里写清"一次调用最多一个字节"。
- **何时该推翻**：如果 X 的 media 对象里开始给字节数，这个 method 降级为兜底；
  但仍保留（CDN 的大小仍可能比 GraphQL 更准）。

## ADR-034 下载路径与参考实现逐项对齐（UA / Referer / 代理 / 多连接）
- **背景**：本仓库是 `x-spider-mac` 的抽取，接进去时"外壳只该改一点点"。
  审计发现下载路径有四处**自己发明的默认值**，每一处都与参考实现不同——
  而其中两处是真实故障源，不是风格差异。
- **决定**：逐项对齐，并且**只对齐可观测行为，不照抄代码结构**：
  1. 下载请求带 `User-Agent`（与参考实现同一个 Chrome 142 字符串）与
     `Referer: https://x.com/`，并显式 `Accept-Encoding: identity`
     （否则服务端压缩时 `Content-Length` 与实际落盘字节数对不上，完整性校验会假红）；
  2. Aria2Next 逐任务带 `all-proxy`（**子进程不吃"跟随环境变量"**，必须给具体 URL）；
  3. `requirements.segments > 1` → `stream-max-connections`
     （上游 aria2 的 `--split` / `--max-connection-per-server` 在 Aria2Next 里已退役）；
  4. 引擎启动参数补上 `--conf-path=/dev/null` 与 DHT/BT 相关的全关
     （不开 UDP，避免防火墙弹窗）；`min_size_for_aria2` 默认 5 MiB（参考实现的默认阈值）。
- **理由**：第 2 条最严重——不传代理时，需要代理才能出网的机器上**外派后端全挂**，
  而内置后端正常，表现为"两个后端行为不一致"；第 1 条在 CDN 端可能直接 403。
- **代价**：组件开始携带一个 UA 字符串（跟随 X 的前端版本会过时）。
- **何时该推翻**：CDN 不再校验 Referer/UA 时（实测一次即可推翻第 1 条）。

## ADR-035 "运行中换代理"对下载路径同样成立
- **背景**：`net.set_proxy` 的承诺是"不必重启进程"，而实测代理端口一天变好几次
  （本地维护手册中记录的代理端口变化）。但下载队列在创建时**快照**了代理——
  换代理后取数恢复、下载仍旧走旧出口，症状是"列表刷得出来、文件一个都下不动"。
- **选项**：A 保持在创建时快照，要求外壳"换代理后重建队列" / B 让两个后端都支持热切换
- **决定**：**B**。`HttpDownloader` 的客户端放进 `RwLock`（`reqwest::Client` 克隆廉价），
  加 `HttpDownloader::set_proxy` / `DownloadQueue::set_proxy`；`Engine::set_proxy` 在
  队列已初始化时一并转发。代理在**派发那一刻**读取，而不是入队那一刻。
- **理由**：一条"运行中可改"的配置，如果只有一半路径生效，比不支持更坏——
  它会让人以为改成功了。
- **代价**：客户端重建有一次分配（只在换代理时发生）。
- **何时该推翻**：不推翻。**已知未覆盖**：`net.set_limits` 的并发上限仍是启动时值
  （信号量换不得），需要时再补。

## ADR-036 M4 的消费者发现：`dl.events` 的事件形状进 schema，`since: 0` 的实现修正
- **背景**：M4（`docs/05` §2）要求"契约在真实使用中未被推翻，若有变更记为 ADR"。
  为此写了一个**只经契约**的 CLI（`bins/xspider-cli`）真跑一遍取数+下载，
  撞到三件事：① `dl.events {since:0}` 被 `invalid_request` 挡回（契约说"从 0 开始"）；
  ② `dl.events` 的事件形状在 schema 里是 `{"items":{"type":"object"}}`（等于没写，
  消费者只能照着散文猜 `kind`/`integrity`）；③ `system.shutdown` 不在 `system.methods` 里。
- **选项**：A 只改实现、契约文档不动 / B 改实现 + 把事件形状补进 schema / C 连 `system.shutdown` 也进能力清单
- **决定**：**B**。①`optional_u64` 允许 0，另加 `optional_positive_u64` 给 `count` 这类
  "0 说不通"的字段（`expect_size` 的 schema `minimum` 本来就是 0，一并修正）；
  ②schema 新增 `$defs/downloadEvent`（`oneOf` 四种，各自 `additionalProperties: false`）
  与 `$defs/integrity`，`dl.events` 的 `items` 指向它，并加契约守卫测试盯字段集合；
  ③**不做**：`system.shutdown` 属于传输层（cdylib 没有"关掉宿主进程"这回事），
  放进能力清单会让 cdylib 承诺一个它做不到的能力。
- **理由**：①契约与实现不一致时错的是实现——文档是别人当作承诺读的那一份，
  而这次的症状最坏（前 3 个任务已入队，才在轮询第一步炸）。
  ②事件是外壳驱动 UI 的唯一数据源，机器可读契约在这里留空，等于把"猜"留给每个消费方。
- **代价**：schema 变大；`count: 0` 与 `since: 0` 的处理现在分属两个辅助函数，读代码时要看清用哪个。
- **何时该推翻**：③如果出现"只有 sidecar 才能做"的能力多到需要机器可读表达，
  就改成 `system.version` 带回 `transport` 字段（`docs/06` §4.2 记了这个提案）。

## ADR-037 `system.version` 带 `transport`，让能力差异可被机器读取
- **背景**：M4 的消费者（CLI）发现：`system.shutdown` 是 sidecar 独有的传输层 method，
  **不在** `system.methods` 里（那份清单只列契约载荷）。代价是外壳必须硬编码
  "我是 sidecar 所以我能关"，而这恰好是"契约该说清却没说"的地方（docs/06 §4.2 记过这个提案）。
- **选项**：A 什么都不做，写进文档让人读 / B 把 `system.shutdown` 塞进 `system.methods` /
  C `system.version` 增加 `transport` 字段
- **决定**：**C**。`Transport::{Sidecar, Cdylib}` 两个值，`Engine` 默认 `Cdylib`
  （直接用 Rust API 就是进程内形态），xspiderd 显式声明 `Sidecar`。
- **理由**：B 会让 cdylib 形态承诺一个它做不到的能力（那就成了"清单说支持、调用失败"，
  比不列更坏）。C 是加法式变更，且**回答了外壳真正要回答的那个问题**：
  "我能不能让它把自己关掉"。CLI 的 `--list-methods` 已经把它打出来并有断言。
- **代价**：契约多一个字段（只增不改不删）；`Engine` 多一个状态位。
- **何时该推翻**：如果将来出现的"形态相关能力"多到需要一张能力矩阵，就把这个字段
  升级成一个能力对象（`{"transport": ..., "capabilities": [...]}`）——现在只有一项，不值当。

## ADR-038 端到端只要求 macOS：三平台 CI 不实跑，改成"能编译"的纪律
- **背景**：ADR-031 写了三平台 CI 的格子，并在 ROADMAP 里诚实标注"**未实跑**"。
  唯一真实存在的消费方是 `x-spider-mac`（macOS），而 Windows/Linux 目前没有第二个消费方。
- **选项**：A 三个平台都跑起来 / B 只保 macOS，其余平台靠"代码里不引入平台专有依赖"的纪律约束
- **决定**：**B**。M3 的验收改为"**macOS 端可用**"（本机 `xsmoke`/`package` 全绿即达标）；
  CI 配置保留但**只跑 macOS 一格**，Windows/Linux 的 job 删掉——留着不跑的 job 等于
  "看起来有覆盖其实没有"，比没有更坏。
- **理由**：跑不起来的 CI 会让人以为覆盖了，而实际覆盖来自"不引入 native-tls / 不用
  Apple 专有框架 / 路径不假设 POSIX"这些**代码级纪律**（它们仍然有效，且由 clippy + 测试守着）。
- **代价**：Windows 的路径/大小写不敏感、`\` 分隔符这类问题**不会被自动发现**，
  要等真的出现第二个消费方时才暴露（风险台账里已记为"中"）。
- **何时该推翻**：出现 macOS 以外的真实消费方时，先加那一格的 CI，再加代码。

## ADR-039 `media` 增加 `poster_url`：视频封面不是可下载文件
- **背景**：接进 `x-spider-mac` 之后**用户实测报"视频无法显示、图片正常"**。
  根因不是我写的代码有 bug，而是**契约少一个字段**：X 对每种媒体都给
  `media_url_https`——对视频/动图那是**封面静帧**，而契约只把它当"图片的下载地址"
  读了一处（`MediaKind::Photo`），视频那三种情况只给"可下载的 mp4"。
  外壳（以及任何界面）需要的是封面：参考实现的 `TwitterMedia.url` 一直就是
  `media_url_https` 语义，界面把它当图片解码（`thumbnailURL(for:)` / `loadHD()`）。
  契约只给 mp4 的后果很具体：视频格子去解码 mp4 → **整片空白**。
- **选项**：A 让外壳自己拼封面地址（做不到：契约里根本没有这个信息） /
  B 把 `url` 改成封面语义、另加 `download_url`（**破坏性**，契约禁止） /
  C 只增一个 `poster_url`
- **决定**：**C**。`media.poster_url`（可空）：封面图；`url` 仍是"可直接下载的地址"，
  两个字段的说明里互相点名，防止再被当成一回事。契约版本 1.1.0 → **1.2.0**。
- **理由**：这是"消费方逼出来的缺口"的典型——组件自测永远发现不了，因为它
  只验证"字段解析对不对"，而"字段够不够"要靠真接一个界面才知道。
  同类风险还有：任何"一种媒体类型读某字段、另一种不读"的地方都值得回头看一眼。
- **代价**：契约多一个字段；外壳侧要记得用 `poster_url` 而不是 `url` 做封面。
- **何时该推翻**：不推翻。**回归测试**在 `ComponentLiveTests.testVideoMediaHasAPosterAndAPlayableURL`
  （断言封面不是 mp4、能被解码成图片、且与播放地址不同）。

## ADR-040 `auth.whoami` / `fetch.is_following` / `fetch.mutate`：把外壳最后一块 HTTP 层收进来
- **背景**：接上取数与下载之后，`x-spider-mac` 里**还有三条路在自己发请求**：
  账户探测（抓 x.com 首页正则取 screen_name）、关注态（v1.1 `friendships/show`）、
  点赞/转推/书签/关注（6 个 GraphQL 突变 + v1.1 form POST）。
  它们拦着 `NetworkClient` / `XClientTransaction` / `RequestGate` 三个文件删不掉——
  而这三个文件正是"每个外壳都会各自重写一遍"的那种代码。
- **选项**：A 留一部分在外壳（比如只搬突变） / B 三块全搬，外壳彻底没有 HTTP 层
- **决定**：**B**。新增三个 method：
  `auth.whoami {}`、`fetch.is_following {screen_name}`、`fetch.mutate {action, tweet_id?/screen_name?}`。
- **理由**：搬一半等于"两个地方都能发请求"，限流/签名/错误分类会各写一套——
  这正是本仓库存在的理由（`docs/01` §1）。另外两处**形状差异**只有搬进来才不会写错：
  突变是"POST + variables 在 query、不带 features"（与搜索的 JSON body 不是一回事），
  关注/取关必须走 `api.twitter.com`（x.com 对 v1.1 friendships 返回 401）。
- **代价**：契约多 3 个 method（26 个了）；组件里多了 `api.twitter.com` 这个主机与
  form-urlencoded 这条路径；`fetch.is_following` 需要"我是谁"，组件因此缓存了账号
  （换 cookie 时清）。
- **何时该推翻**：如果某个平台要求"写操作必须由外壳亲自发起"（例如平台侧审计），
  那就把 `fetch.mutate` 降级成 `dl.plan` 那样的"产描述、由外壳执行"。

## ADR-041 契约 1.5.1 的四个修复：错误透传、事件归属、`--state-dir`、记录落盘原子性
- **背景**：一轮审计在组件里发现四处"实现与契约对不上"，且都是**实现没做到文档已经承诺的事**，
  不是要改契约语义。按铁律 1，先改契约/文档（本 ADR 是这一轮的设计依据），再改代码。
  四条**都不增删 method / 字段 / 错误码**，属 PATCH：契约版本 1.5.0 → **1.5.1**。
- **四条修复与对外可见性**：
  1. **`crawl.run` 的取页错误被吞成 `internal`**（`crates/xspider-download/src/crawl.rs` 的
     `map_err`）——**改对外行为**。修后保留原始 `ErrorCode` 与结构化字段
     （`retry_after_s` / `status` / `context` / `endpoint` / `detail`），页号只进 `message`。
     这正是 §5 早已规定的结构化错误模型，此前只有 `crawl.run` 这一条路破坏它。
     **不改 error 字段集合**：`$defs/error` 是 `additionalProperties:false`，加字段会触发
     契约守卫（`contract_guard.rs` 逐个核对字段集合），所以页号只能放 `message`。
  2. **`crawl.run` 的 `events` 取进程级累积**（`crates/xspider-ffi/src/engine.rs` 取
     `crawl_log.since(0)`，环形缓冲从不清理）——**改对外行为**。`events` 收敛为**本次调用**，
     `seq` 仍进程内单调、不回退（下界从 0 改为调用前的 seq）。与 `docs/CONTRACT.md` §4.14、
     `docs/07` §4.5 早已写的"本轮"一致。schema 里 `seq`/`events` 无逐字段约束，结构不必动。
  3. **`--state-dir` 不决定下载记录路径**（`bins/xspiderd/src/main.rs` 只拿它取实例锁；
     `records_path` 只认 `XSPIDER_STATE_DIR`，`engine.rs`）——**改 CLI/sidecar 行为，
     不改契约载荷**。修后 `--state-dir` 同时决定 `records_path`，**flag 优先**于环境变量；
     实例锁仍只由 `--state-dir` 触发。这是让"文档早就这么写"成立，而非新增能力。
  4. **下载记录落盘非原子**（`crates/xspider-download/src/queue.rs` 的 `write_record_shared`：
     先解锁 insert、再重新 clone 整表写盘；并发写者共用同一个 `.tmp`）——**纯内部修复，
     对外不可见**。修后"快照 + 写盘"在同一把写锁内完成，临时文件名唯一再 rename。
     `downloads.json` 的格式与 `RECORDS_VERSION` 不变。
- **选项**：A 只改实现、文档不动 / B 文档与实现一起改 / C 改契约语义。
  **决定：B**。四条都是"实现偏离已承诺行为"，契约条文不改语义、只补精确措辞；
  C 不成立——没有任何一条需要改 method / 字段 / 错误码。
- **理由**：契约与实现不一致时错的是实现（ADR-036 已确立）。逐条的可观测后果都很具体：
  `internal` 让外壳把"重新登录"当成"组件 bug"；进程级事件让按推荐方式"小页数反复调用"的
  外壳重复处理历史事件；`--state-dir` 不落记录让"它在管记录"成为假文档；非原子写让并发完成时
  丢记录，而记录是决定"重启后能不能对账"的资产（踩坑 28，见 docs/05-WORKFLOW.md 的踩坑总索引；铁律"记录是契约级资产"）。
- **代价 / 已知缺口（本轮**不**修，必须写清）**：
  1. `write_record_shared` 的生产调用点只有"完成"那一处（`finish_job` 的 Ok 分支），
     **未完成 / 暂停 / 失败的记录从不落盘**——所以 `load_records` 的"恢复未完成任务"
     分支在生产里是死代码，"重启续传未完成任务"尚未生效。第 4 条只修"已完成记录的写是
     原子的"，**不修**这个缺口。已在 `docs/CONTRACT.md` §4.13、`docs/07` §2.2、
     `docs/08` §5.3 与 `docs/ROADMAP.md` 风险台账标注。
  2. 记录路径的**跨进程互斥**仍不足：实例锁只在传 `--state-dir` 时获取，而真实外壳只传
     `--port 0` + `XSPIDER_STATE_DIR`（`x-spider-mac` 的 `XSpiderComponent`）——这条路径
     **没有锁**，两个共享同一 `XSPIDER_STATE_DIR` 的 sidecar 仍会交错写整表快照、丢更新。
     即第 4 条的正确性依赖"同目录只有一个写者"，而这一点当前**不保证**；唯一临时名只避免
     `.tmp` 互踩，不避免丢更新。多实例安全需要"env 也触发锁"或按文件加锁，属后续工作。
  3. `crawl.run` 取消存在**两种可观测形态**（页边界察觉 → `done_reason:"cancelled"`；
     取页在飞行中被取消 → `error.code:"cancelled"`）。本轮决定**如实写进契约**（两种都按
     取消处理），而不是强行归一化——归一化要动 `source` 闭包的错误路径，超出本轮范围。
- **何时该推翻**：
  ① 若产品要求"未完成任务也能重启续传"，就必须先把 Waiting/Active/Paused 状态的记录落盘，
    并补一条"暂停/中断后重启 → `load_records` 恢复"的 E2E；届时缺口 1 作废；
  ② 若外壳开始给 sidecar 传 `--state-dir`（或锁改为 env 也触发），缺口 2 作废；
  ③ 若后来决定 crawl 取消只保留一种形态，缺口 3 的措辞随之收窄。

## ADR-042 安卓增量接入与 1.5.2 实现修正（2026-10-05）
- **背景**：安卓复用报告指出构建/打包缺位、native-roots 仅发现 Termux CA、可写目录禁止执行、状态记录仅完成时落盘。编译失败经复核为 Homebrew rustc 环境误报。
- **决定**：保留全部 26 个 method、三个 C ABI 导出与 macOS 信任根/引擎路径；仅安卓启用公共 webpki 根，增加独立 NDK 构建打包及验证链路。安卓先走 sidecar + 内置 HTTP 后端，JNI cdylib 作为有明确生命周期约束的备选，不凭纸面推断改变 macOS 主形态。ADR-038 的 macOS 验收保留，额外加入安卓构建及离线设备冒烟，不声称安卓 live 已验收。
- **实现修正**：crawl 的缺省 next_cursor 省略；状态转换落盘并恢复未完成任务；`XSPIDER_STATE_DIR` 也取得 sidecar 实例锁；Unix 用内核 `flock`，锁文件保留 inode，存在不代表正在运行，进程结束后内核自动解锁，不调用 PATH 上的 kill 探测；`XSPIDER_ARIA2_DIR` 显式覆盖默认临时目录。
- **下载并发与清理**：每个任务的后端 I/O 串行持有文件，过期 dispatch 校验 epoch 后退出；取消清理失败后保留意图，允许再次取消收尾。完整目标文件仅在自身后端已成功落盘且被取消的竞态中处理；暂停/等待取消及崩溃恢复不删除无法确认归属的完整文件。旧 version 1 记录缺少的新元数据采用保守默认值，不依赖文案判断。
- **兼容性**：1.5.2 PATCH，不新增方法/字段/错误码；version 1 记录仍可读。`waiting` / `active` 的 `dl.resume` 保持成功但不重复派发；`paused` / `error` 可显式恢复，`complete` 拒绝恢复；取消清理期间暂拒恢复。取消记录不自动恢复，但清理结束后用户可显式 resume；mac 外壳启动对账与暂停策略继续成立。
- **边界**：安卓后台服务、MediaStore、登录凭据持久化属于外壳；前台服务不保证子进程永远存活，必须对账恢复。C ABI 阻塞调用放后台线程，无取消/销毁导出；不将 JNI 类型纳入契约。
- **何时该推翻**：真实安卓消费方证明子进程方案无法满足产品生命周期时，再以加法 method 设计 cdylib 初始化与取消能力，并补双形态测试。
